이 가이드가 하는 일문제 · 방법 · 전체 그림

AOAI(Azure OpenAI)를 호출하는 앱의 응답이 가끔 느릴 때, ‘느리다’는 사실만으로는 원인을 알 수 없습니다. 시간이 쓰일 수 있는 곳이 세 군데이기 때문입니다. (아래 R1~R8 은 이 가이드가 로그 수집 항목에 붙인 번호입니다: R1 AOAI 진단 로그 · R2 AOAI 메트릭 · R3 앱 호출 로그 · R4 Application Insights · R5 VM 모니터링 에이전트 · R6 네트워크 경로 · R7 합성 probe · R8 알림. 자세한 표는 아래에 있습니다.)

  • 요청 한 건마다 앱이 잰 시간과 AOAI 가 잰 시간을 비교해, 느린 시간이 AOAI 안인지 바깥(연결 · 네트워크)인지 구분한다.
  • 느린 시각이 정각 · 30분에 도는 배치 작업(cron) 이나 VM 부하와 겹치는지 확인하는 방법을 익힌다(이 실습 데이터는 1시간 남짓이라 실제 패턴은 나오지 않습니다).
  • 느림 · 실패가 생기면 이메일 알림을 받고, 그 순간의 VM 상태 스냅샷을 남긴다.

Azure OpenAI 와 호출

Azure OpenAI (AOAI)

Azure 에서 OpenAI 모델(GPT 등)을 API 로 호출해 쓰는 서비스입니다. 앱은 https://<이름>.openai.azure.com 주소로 요청을 보냅니다.

리전 · 엔드포인트

리전은 리소스가 있는 Azure 의 위치(예: koreacentral = 한국 중부)이고, 엔드포인트는 호출 주소(https://<이름>.openai.azure.com)입니다.

배포 (deployment)모델 배포

모델(예: gpt-4.1-mini)을 호출할 수 있는 이름으로 만들어 둔 것입니다. 앱은 모델 이름이 아니라 ‘배포 이름’으로 호출하고, 배포마다 처리 한도(TPM)가 있습니다.

SDK · 스트리밍

SDK 는 앱이 AOAI 를 부르게 해 주는 라이브러리(이 가이드는 Python openai 패키지)입니다. 스트리밍은 응답을 다 만든 뒤 한 번에 받는 대신 생성되는 대로 조각으로 받는 방식입니다. 이 실습은 한 번에 받는 방식이며, 스트리밍이면 total_ms 의 의미가 달라집니다.

SKU · Global Standard

SKU 는 리소스의 ‘등급 · 요금 방식’입니다. 모델 배포의 Global Standard 는 여러 리전의 용량을 함께 쓰는 종량제(쓴 토큰만큼 과금) 방식입니다.

TPM · 쿼터tokens per minute

배포가 1분에 처리할 수 있는 토큰 수의 한도입니다(이 가이드의 단위는 1K = 1,000). 한도를 넘으면 429(너무 많은 요청) 오류가 납니다.

토큰

모델이 글자를 처리하는 단위입니다(한글 한 글자는 대략 1~2토큰). 처리 시간과 요금이 토큰 수에 비례하므로 응답이 길수록 오래 걸립니다.

HTTP 상태 코드

200 성공 · 404 대상 없음(배포 이름 오타 등) · 429 한도 초과 · 499 서버가 응답하는 도중 클라이언트(앱)가 연결을 끊음(AOAI 로그에서 쓰는 값) · 5xx 서버 오류.

timeout시간 제한

앱(SDK)이 응답을 기다려 주는 시간 제한입니다. 연결 · 요청 전송 · 응답 읽기 단계마다 따로 정하며, 넘으면 앱이 스스로 포기합니다(이 가이드의 기록에서는 client_timeout).

api-version

AOAI 호출 주소 끝에 붙이는 API 버전(예: api-version=2024-10-21)입니다. 앱 · probe 가 같은 버전으로 호출해야 같은 동작을 합니다.

지연 · p95latency

요청이 걸린 시간이 지연입니다. p95 는 ‘가장 느린 5% 를 뺀 나머지 중 최댓값’으로, 평균에 묻히는 느린 쪽을 보려고 씁니다.

추론 모델reasoning model

답을 내기 전에 내부 추론 과정을 거치는 모델(예: gpt-5 계열)입니다. max_tokens 대신 max_completion_tokens 를 요구하는 등 호출 옵션이 다릅니다(A3 의 경고).

로그 · 모니터링

Log Analytics 워크스페이스workspace

Azure 의 로그 저장소입니다. 여러 곳의 로그를 한곳에 모아 두고 KQL 로 조회합니다.

KQLKusto Query Language

Log Analytics 워크스페이스 · Application Insights 를 조회하는 질의 언어입니다. 테이블 | 단계 | 단계 처럼 파이프(|)로 단계를 이어서 위에서 아래로 읽습니다. 자주 쓰는 단계: where 거르기 · extend 계산한 열 추가 · project 열 고르기 · summarize … by 묶어서 집계 · join 키로 두 표 잇기 · union 표 합치기 · top 상위 N건. p50 · p95 는 ‘절반 · 95% 의 호출이 이 시간 이하’라는 뜻이라, p95 는 느린 쪽 5% 의 경계입니다.

Application Insights앱 모니터링

앱의 외부 호출 기록과 로그를 모아 주는 서비스입니다. ‘워크스페이스 기반’으로 만들면 데이터가 위 워크스페이스의 AppDependencies(외부 호출) · AppTraces(앱 로그) 같은 테이블에 저장됩니다.

진단 설정Diagnostic settings

Azure 리소스(예: AOAI)가 스스로 만드는 로그 · 메트릭을 워크스페이스로 보내도록 켜는 설정입니다. 앱 코드는 바뀌지 않습니다.

메트릭 vs 로그

메트릭은 1분 단위로 집계된 숫자(가볍고 알림에 빠름), 로그는 요청 한 건마다의 상세 기록입니다. 이 가이드는 둘 다 모읍니다.

OpenTelemetry (OTel)

앱의 외부 호출과 로그를 표준 방식으로 수집하는 오픈소스 계측 도구입니다. azure-monitor-opentelemetry 가 이를 Application Insights 로 보냅니다.

샘플링sampling

호출을 전부 기록하지 않고 일부만 기록하는 것입니다. 호출이 많을 때 비용을 줄이는 기능인데, 진단 기간에는 빠지는 호출이 없도록 끕니다(R4 의 always_on).

요청 IDapim-request-id

요청 한 건을 가리키는 값입니다. AOAI 응답 헤더 apim-request-id 는 AOAI 진단 로그의 CorrelationId 와 같아서, 앱 기록과 AOAI 기록을 한 건씩 짝지을 수 있습니다.

알림 규칙 · 액션 그룹

조건(예: 499 가 1건 이상)을 계속 감시하다가 충족하면 알려 주는 규칙과, 알릴 곳(이메일 등)을 모아 둔 수신 그룹(= 액션 그룹) 입니다.

수집 지연ingestion latency

로그가 생긴 뒤 워크스페이스에서 조회되기까지 걸리는 시간입니다. 실측: 앱 약 10초 · VM 약 2분(수집 규칙을 연결한 뒤 처음 나타나기까지는 5~10분) · AOAI 로그 평균 약 2분(처음 켠 뒤 20~26분은 비어 있음) · 메트릭 7~10분.

UTC · KST

로그의 시각은 UTC(협정 세계시)로 저장 · 표시됩니다. 한국 시각(KST) = UTC + 9시간이라 분은 같고 시(時)만 9시간 차이입니다(예: UTC 13:26 = KST 22:26).

가용성 테스트availability test

Application Insights 가 외부에서 주기적으로 URL 을 호출해 살아 있는지 보는 기능입니다. 내 환경에 이미 있을 수 있습니다(부록 E 의 avail_tests).

Support Case

Azure 지원팀에 보내는 지원 요청입니다(포털 → 도움말 + 지원). AOAI 쪽 문제가 의심될 때 이 가이드가 모은 요청 ID · 시각 · 메트릭을 첨부합니다.

VM · 네트워크 · 권한

Azure Monitor Agent (AMA) · 수집 규칙 (DCR)Data Collection Rule

VM 안에 설치되어 성능 카운터 · syslog 를 Azure 로 보내는 프로그램(AMA)과, ‘무엇을 어디로 보낼지’ 적어 둔 규칙(DCR)입니다.

syslog facility

syslog 로그가 속한 채널 이름입니다(예: cron = cron 작업, local0~local7 = 사용자 정의용). 이 가이드는 probe 의 기록에 local5 를 쓰고, 수집 규칙이 cron 과 local5 만 가져옵니다.

관리 IDManaged Identity

VM 같은 Azure 리소스에 자동으로 붙는 신원입니다. 키나 비밀번호 없이 ‘역할’을 받아 다른 서비스를 호출합니다.

Microsoft Entra ID

Azure 의 계정 · 신원 서비스(예전 이름 Azure AD)입니다. 키 대신 ‘관리 ID’ 같은 신원으로 인증하는 방식이 여기에 해당합니다.

역할 (RBAC)Role-based access control

누가 무엇을 할 수 있는지 정하는 Azure 권한입니다. 예: Cognitive Services OpenAI User = AOAI 를 호출할 수 있음.

systemd · journald

Linux 에서 서비스와 타이머를 관리하는 프로그램이 systemd 입니다(서비스 파일의 [Unit] · [Service] · [Install] 은 구역 이름). 서비스가 출력한 로그를 모아 두는 곳이 journald 이고 journalctl -u 서비스이름 으로 봅니다. 타이머(.timer)는 같은 이름의 .service 를 정해진 시각에 실행합니다.

syslog · cron

syslog 는 Linux 가 로그를 남기는 표준 통로(채널 이름 = facility)이고, cron 은 정해진 시각에 작업을 실행하는 도구입니다. 이 가이드는 cron 의 실행 기록과 probe 의 기록(local5)을 syslog 로 수집합니다.

합성 probesynthetic probe

사용자 요청과 상관없이 1분마다 같은 작은 호출을 보내 구간별 시간을 재는 점검 스크립트입니다. 평소 기준선이 생겨 ‘지금이 느린 건지’ 판단할 수 있습니다.

DNS · TCP · TLS

DNS 는 이름(xxx.openai.azure.com)을 IP 주소로 바꾸는 조회, TCP 는 두 컴퓨터가 연결을 맺는 단계, TLS 는 그 연결을 암호화하는 협상입니다. 요청 한 건은 보통 DNS → TCP 연결 → TLS 협상 → 요청 전송 → 서버 처리 → 응답 순서로 진행되어, 느린 구간을 이 단계별로 나눠 볼 수 있습니다.

NAT · 방화벽 · 프록시

방화벽은 허용된 접속만 통과시키는 장치, 프록시는 접속을 대신 전달해 주는 중간 서버, NAT 는 사설 IP 의 VM 이 인터넷으로 나갈 때 공용 IP 로 주소를 바꿔 주는 것입니다. 이런 장치가 VM 과 AOAI 사이에 있으면 지연이 생길 수 있어 B7 에서 따로 봅니다.

Connection Monitor · flow logNetwork Watcher

VM 에서 목적지(AOAI 443 포트)까지 연결 시간 · 실패율을 주기적으로 재는 기능, 그리고 VNet 안 트래픽 흐름을 기록하는 기능입니다.

RTTround-trip time

신호가 갔다가 돌아오는 왕복 시간입니다. 같은 리전의 TCP 연결은 보통 몇 ms 입니다.

FQDNfully qualified domain name

전체 도메인 이름(예: <이름>.openai.azure.com)입니다. 방화벽 규칙이 IP 대신 이 이름으로 허용 · 차단합니다.

SNAT 포트

사설 IP 의 VM 이 인터넷으로 나갈 때 공용 IP 의 포트를 빌려 쓰는 것(주소 변환)입니다. 빌려 쓸 포트가 고갈되면 새 연결이 느려지거나 실패합니다.

NVA · UDR

NVA 는 가상 네트워크 안의 타사 네트워크 장비(방화벽 가상 어플라이언스 등), UDR 은 트래픽을 그 장비로 보내도록 정하는 사용자 정의 경로입니다.

구독 · 리소스 그룹subscription · resource group

구독은 요금과 권한의 기본 단위, 리소스 그룹은 리소스를 담는 폴더입니다. 그룹을 지우면 안의 리소스가 모두 지워져 정리가 쉽습니다.

7도우미 함수 ① vmrun — VM 안에서 명령 실행

>> 는 파일 끝에 덧붙이기, <<'EOF'(따옴표 있는 EOF)는 변수를 바꾸지 않고 글자 그대로 쓰라는 뜻입니다. 함수 안의 $RG · $VM 은 함수를 부를 때 그때의 값으로 해석되어야 하기 때문입니다.

vmrun 은 VM 안에서 스크립트를 실행하는 함수입니다. 사용법은 vmrun <<'X' 아래에 실행할 스크립트를 적고 X 로 끝내는 것입니다.

local s; s="$(cat)"
local 은 ‘이 함수 안에서만 쓰는 변수’이고, $(cat) 은 표준입력(heredoc)으로 들어온 스크립트를 읽어 s 에 담습니다.
az vm run-command invoke … --command-id RunShellScript --scripts "$s"
Azure 가 VM 에 설치된 에이전트(Azure VM 에이전트, waagent)를 통해 스크립트를 VM 안에서 root 권한으로 실행합니다(그래서 뒤의 dnf 를 sudo 없이 씁니다). SSH 접속이 필요 없고 VM 에 인바운드 포트를 열 필요도 없습니다.
--parameters "$@"
$@ 는 함수에 넘긴 인자 전체입니다. vmrun AOAI_HOST=값 DEP=값 처럼 넘긴 이름=값 들을 VM 안 스크립트가 $이름 으로 쓸 수 있게 전달합니다. 인자가 하나도 없으면($# 가 0) 이 부분을 뺍니다 — 앞의 if [ $# -gt 0 ] 가 그 판단입니다.
--query "value[0].message" -o tsv
실행 결과(표준출력)만 글자 그대로 출력합니다.

# R3_aoai_call_log.py - AOAI 호출 1회(시도)마다 JSON 1줄을 남기는 헬퍼. 프로젝트에 한 번 추가합니다.
# 요구: Python 3.9+ / openai 패키지 (AzureOpenAI). 프롬프트·응답 본문은 기록하지 않습니다(메타데이터만).
import json, logging, threading, time, uuid
from contextlib import contextmanager

log = logging.getLogger("aoai.call")       # 파일·App Insights(R4)로
_lock, _busy = threading.Lock(), 0
ERR = {"APITimeoutError": "client_timeout"}    # 그 외 예외는 "error"

@contextmanager
def call_log(**fields):
    global _busy
    with _lock:
        _busy += 1
        n = _busy                       # 시작 시점의 동시 호출 수
    rec = {"event": "aoai_call", "cid": str(uuid.uuid4()),
           "inflight": n, **fields}
    t0 = time.perf_counter()
    try:
        yield rec
        rec["outcome"] = "ok"
    except Exception as e:              # 기록 후 예외는 그대로 전달
        rec.update(outcome=ERR.get(type(e).__name__, "error"),
                   error=type(e).__name__,
                   status=getattr(e, "status_code", None),
                   request_id=getattr(e, "request_id", None))
        raise
    finally:
        with _lock:
            _busy -= 1
        rec["total_ms"] = round((time.perf_counter() - t0) * 1000)
        log.info(json.dumps(rec, ensure_ascii=False))

emit() {  # $1=대상  $2=curl 종료코드  $3=write-out 문자열 (curl 시간값은 누적이므로 차이를 구해 구간별로 기록)

      tcp_ms = (c > d) ? c - d : 0; tls_ms = (t > c) ? t - c : 0; base = (t > 0) ? t : c;
      wait_ms = (f > base) ? f - base : ((f == 0 && T > base) ? T - base : 0);
      printf "{\"event\":\"aoai_probe\",\"role\":\"%s\",\"target\":\"%s\",\"rc\":%d,\"code\":\"%s\",\"dns_ms\":%d,\"tcp_ms\":%d,\"tls_ms\":%d,\"wait_ms\":%d,\"total_ms\":%d,\"ip\":\"%s\",\"new_conns\":%d}",
             role, tgt, rc, code, d*1000, tcp_ms*1000, tls_ms*1000, wait_ms*1000, T*1000, ip, cn }')

B7 · R6네트워크 경로 로그 — Connection Monitor · VNet flow log · (선택) Azure Firewall선택 · 조건부 적용

소요 약 5분 (Firewall 포함 시 약 25분) · 필요한 권한: VM 확장 설치 · Network Watcher 리소스 생성(예: Virtual Machine Contributor + Network Contributor) · 저장소 계정 생성

무엇을 하나요

VM → AOAI 경로의 로그를 모읍니다. Connection Monitor 는 VM 에서 AOAI 443 포트로 TCP 연결 시간(RTT)과 실패율을 30초마다 재고, VNet flow log 는 연결 수 · 바이트를, Azure Firewall 진단 로그는 FQDN 규칙 · DNS · SNAT 포트 사용률을 줍니다.

왜 필요한가요

앱과 probe(VM 안)가 느린데 probe(VM 밖)는 정상일 때 경로(방화벽 · DNS · SNAT) 가 의심됩니다. 그때 쓰는 로그입니다.

끝나면

NWConnectionMonitorTestResult 테이블에 30초마다 RTT 가 쌓이고, VNet flow log 가 켜집니다.

내 환경에서는

경로에 Azure Firewall 이 있으면 방화벽 진단 설정(아래 ‘다’ 부분)을 내 방화벽에 그대로 적용합니다(허브 구독 권한 필요). 방화벽이 아닌 타사 NVA 라면 세션 수 · SNAT 풀 사용률 · 연결 실패 로그를 벤더 기준으로 요청해야 합니다. Network Watcher 가 해당 리전에 있어야 하고, 저장소는 같은 리전의 Standard 계정이어야 합니다. 리전이 koreacentral 이 아니면 아래 명령의 -l koreacentral(2곳)을 내 리전으로 바꾸세요.

이 단계는 꼭 해야 하나요? — 경로가 의심될 때 필요합니다

앱과 probe(VM 안)가 느린데 VM 밖 probe 는 정상이거나, VM 에서 AOAI 로 가는 길에 방화벽 · 프록시 · NAT 가 있을 때 필요합니다. 그런 의심이 없으면 B7 은 건너뛰고 나중에 필요할 때 해도 됩니다. 세 가지로 나뉩니다.

  • 가. Connection Monitor — VM → AOAI 연결(TCP)에 걸린 왕복 시간(RTT)과 실패율을 30초마다 잽니다. 가장 쓸모가 큽니다.
  • 나. VNet flow log — 네트워크 안의 연결 수 · 바이트를 기록합니다(지연 정보는 없음).

끝나면

요청별로 outcome · status · app_ms · aoai_ms · gap_ms 가 나옵니다(gap 이 큰 순서).
