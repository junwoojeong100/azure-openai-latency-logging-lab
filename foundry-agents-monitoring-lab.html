Foundry 와 에이전트

Azure OpenAI (AOAI)

Azure 에서 OpenAI 모델(GPT 등)을 API 로 호출해 쓰는 서비스입니다. 앱은 https://<이름>.openai.azure.com 주소로 요청을 보냅니다.

Microsoft Foundry

AI 앱 · 에이전트 · 모델 배포를 한곳에서 만들고 운영하는 Azure 서비스입니다. 모델을 직접 호출하는 대신 ‘에이전트’를 통해 호출할 수 있습니다.

Foundry 프로젝트project

Foundry 안에서 에이전트 · 모델 배포 · 연결(예: Application Insights)을 묶어 두는 작업 공간입니다. 호출 주소(엔드포인트)도 프로젝트마다 하나입니다.

Foundry Models · 모델 배포

Foundry 에서 모델(여기서는 gpt-5.4-mini)을 배포한 것입니다. 기존 AOAI 의 ‘배포’와 같은 개념이며, 호출 한도(쿼터)도 배포 단위입니다.

에이전트agent

모델 + 지시문(+ 도구)을 하나로 묶어 이름을 붙인 것입니다. 앱은 에이전트 이름으로 호출하고, 에이전트가 모델을 부릅니다. 이 가이드는 ‘코드가 없는’ 프롬프트 에이전트와 ‘코드로 만든’ 호스티드 에이전트 두 가지를 씁니다.

호스티드 에이전트 · MAFHosted agent · Microsoft Agent Framework

내가 쓴 Python 코드(MAF = Microsoft Agent Framework)를 Foundry 가 컨테이너로 실행해 주는 에이전트입니다. 코드로 도구·흐름을 직접 짤 수 있는 대신, 새 대화마다 컨테이너를 띄우는 cold start 가 있습니다.

cold start · warm

컨테이너를 새로 띄우느라 첫 호출이 느린 것이 cold start, 이미 떠 있어 빠른 호출이 warm 입니다. 호스티드 에이전트는 새 대화(세션)마다 cold start 가 일어납니다. 이번 실측: 시작 지연이 약 7초이고, 그 호출의 총 응답 시간은 약 8~12초였습니다.

Responses API · Chat Completions API

OpenAI 모델을 부르는 두 가지 호출 규격입니다. 기존 AOAI 앱은 보통 Chat Completions(chat.completions.create)를, 에이전트는 Responses(responses.create)를 씁니다.

Entra ID · Foundry User 역할

이 가이드는 API 키 없이 az login 한 내 계정(Entra ID) 으로 호출합니다. 호출하려면 프로젝트에 Foundry User 역할이 필요합니다(azd up 중에 자동으로 부여).

트레이스 · 로그

텔레메트리telemetry

서비스나 앱이 스스로 남기는 측정 기록(요청 · 걸린 시간 · 오류 · 로그)의 총칭입니다. 이 가이드에서 ‘텔레메트리 코드’는 그런 기록을 남기려고 앱이나 에이전트에 넣는 코드를 말합니다.

서버 쪽 · 앱 쪽

이 가이드에서 ‘서버 쪽’은 Foundry(에이전트 + 모델), ‘앱 쪽’은 내 코드와 그 코드가 도는 컴퓨터(VM 등) 입니다. ‘서버 트레이스’는 Foundry 가 남기는 기록을 뜻합니다.

트레이스 · 스팬trace · span

요청 한 건이 지나간 전체 경로가 트레이스, 그 경로의 한 구간(예: 에이전트 실행, 모델 호출)이 스팬입니다. 구간마다 시작 시각과 걸린 시간이 기록됩니다.

trace_id · traceparent · operation_Id

trace_id 는 요청 한 건의 이름표입니다. 앱이 traceparent 라는 요청 헤더에 trace_id 를 실어 보내면, Application Insights 에서는 operation_Id 로 조회됩니다. 앱 기록과 서버 기록을 같은 값으로 짝지을 수 있습니다.

invoke_agent · chat 스팬

플랫폼이 남기는 두 가지 스팬입니다. invoke_agent = 에이전트 실행 전체, chat = 그 안의 모델 호출. invoke_agent − chat 이 에이전트 런타임이 쓴 시간(오버헤드)입니다.

Application Insights · Log Analytics트레이스 저장소

Application Insights 는 앱 · 에이전트가 남긴 기록을 보여 주는 모니터링 서비스이고, Log Analytics 워크스페이스는 그 기록이 실제로 저장되는 곳입니다(A2 의 스크립트가 둘을 만들어 연결합니다). 기록은 requests(받은 요청) · dependencies(다른 곳에 시킨 일) · traces(로그) · exceptions(예외) 테이블에 쌓이고 KQL 로 조회합니다. 프로젝트에 연결만 되어 있으면 두 에이전트의 서버 쪽 트레이스가 코드 없이 쌓입니다.

requests · dependencies · traces · exceptions

Application Insights 의 네 테이블입니다. requests = 서비스가 받은 일, dependencies = 서비스가 다른 곳에 시킨 일(외부 호출), traces = 로그 메시지, exceptions = 예외. 같은 에이전트 실행이 두 테이블에 함께 남기도 합니다(C2).

역할 이름 vs 역할

역할 이름(cloud_RoleName) 은 기록을 보낸 쪽의 이름표입니다(예: responsesapi). 역할(RBAC) 은 권한입니다(예: Foundry User). 말은 비슷하지만 전혀 다른 것입니다.

OpenTelemetry (OTel)

서비스의 호출과 로그를 표준 방식으로 수집하는 오픈소스 계측 규격 · 도구입니다. trace · span · traceparent(요청 한 건의 이름표를 헤더로 전달) · gen_ai.*(AI 호출의 속성 이름) 같은 이름이 이 규격에서 나왔습니다. 호스티드 에이전트 컨테이너는 시작할 때 이것을 스스로 설정해 트레이스를 Application Insights 로 보냅니다.

KQLKusto Query Language

Log Analytics 워크스페이스 · Application Insights 를 조회하는 질의 언어입니다. 테이블 | 단계 | 단계 처럼 파이프(|)로 단계를 이어서 위에서 아래로 읽습니다. 자주 쓰는 단계: where 거르기 · extend 계산한 열 추가 · project 열 고르기 · summarize … by 묶어서 집계 · join 키로 두 표 잇기 · union 표 합치기 · top 상위 N건. p50 · p95 는 ‘절반 · 95% 의 호출이 이 시간 이하’라는 뜻이라, p95 는 느린 쪽 5% 의 경계입니다.

UTC · KST

로그의 시각은 UTC(협정 세계시)로 저장 · 표시됩니다. 한국 시각(KST) = UTC + 9시간이라 분은 같고 시(時)만 9시간 차이입니다(예: UTC 13:26 = KST 22:26).

수집 지연ingestion latency

트레이스가 생긴 뒤 조회되기까지 걸리는 시간입니다. 이 가이드 실측: 마지막 호출이 약 11초 뒤에 보였고, 텔레메트리 799건 중 중앙값 약 6초 · 96% 가 1분 안 · 최대 약 2분 40초입니다(C1).

알림 규칙 · 액션 그룹

조건(예: 실패한 실행이 1건 이상)을 주기적으로 확인하다가 충족되면 알려 주는 규칙과, 알릴 곳(이메일 등)을 모아 둔 수신 그룹(액션 그룹)입니다(D1).

앱 최소 기록

앱이 에이전트를 부를 때마다 직접 남기는 로그 한 줄(trace_id · 클라이언트가 잰 시간 · 상태/오류 · 재시도)입니다. 서버 트레이스에 없는 구간(앱 ↔ Foundry)을 메웁니다. 코드는 약 10~15줄로 예상합니다(이번에 검증하지 않음). C7 에서 설명합니다.

azd (Azure Developer CLI)

azure.yaml 한 파일에 적은 대로 프로젝트 · 모델 · 에이전트를 만들고(azd up) 지우는(azd down) 명령줄 도구입니다. az 와 로그인이 따로입니다.

프로비저닝 · 배포provision · deploy

프로비저닝은 Azure 리소스를 실제로 만드는 일, 배포는 그 위에 에이전트를 올리는 일입니다. azd up = 프로비저닝 + 배포를 한 번에 합니다.

구독 · 리소스 그룹subscription · resource group

구독은 요금과 권한의 기본 단위, 리소스 그룹은 리소스를 담는 폴더입니다. 그룹을 지우면 안의 리소스가 모두 지워져 정리가 쉽습니다.

TPM · 쿼터tokens per minute

배포가 1분에 처리할 수 있는 토큰 수의 한도입니다(이 가이드의 단위는 1K = 1,000). 한도를 넘으면 429(너무 많은 요청) 오류가 납니다.

HTTP 상태 코드

200 성공 · 400 잘못된 요청(요청 옵션이 허용되지 않을 때 등) · 404 대상 없음(배포 이름 오타 등) · 429 한도 초과 · 5xx 서버 오류. 이 가이드의 에이전트 응답은 HTTP 200 이어도 status 가 failed 일 수 있습니다(D2).

timeout시간 제한

앱(SDK)이 응답을 기다려 주는 시간 제한입니다. 넘으면 앱이 스스로 포기하고 예외가 납니다 — 앱 최소 기록(C7)에서 잡아야 하는 경우입니다.

R1 ~ R8

짝 가이드(가이드 1)가 따르는 로그 수집 항목 번호입니다: R1 AOAI 진단 로그 · R2 메트릭 · R3 앱 호출 로그 · R4 Application Insights · R5 모니터링 에이전트(AMA) · R6 네트워크 경로 · R7 합성 probe · R8 알림. 이 가이드와의 대응은 E1 표에 있습니다.

서버(에이전트 · 모델)가 정상이어도 사용자는 느리다고 느낄 수 있습니다. 그 차이가 어디서 생기는지는 서버 트레이스만으로는 알 수 없어서, 앱 쪽에도 호출 1건당 한 줄의 기록이 필요합니다.

끝나면

클라이언트 − 서버 시간 차(표 1), 429 후 재시도 대기 사례(표 2), 앱 최소 기록에 담을 4가지.

내 환경에서는

내 앱의 에이전트 호출부에 호출 1건당 한 줄을 남기세요(약 10~15줄, 추정). invoke_agents.py 가 출력하는 JSON 한 줄이 그 예이고, 아래 ③ 에 예외까지 남기는 스케치가 있습니다.

읽는 법

SDK 가 429 를 받고 약 4.6초 기다렸다가 다시 보낸 기록입니다(2회까지 재시도). 이 대기는 클라이언트에서만 보입니다.

  • 표의 두 번째 행은 재시도 2번(약 5초 · 6초 대기) 끝에도 429 로 실패해 RateLimitError 가 난 경우입니다. 클라이언트는 11,405ms 를 기다렸지만 서버 스팬은 1ms 짜리 실패 3건뿐입니다. 한도가 큰 배포에서는 재현되지 않을 수 있습니다.
  • 서버에는 실패 스팬(1ms) 과 성공 스팬(945ms) 만 있고, 둘 사이 약 4.6초(재시도 대기) 는 서버 트레이스에 없습니다. 그래서 클라이언트는 5,838ms 를 느꼈습니다.
  • 이 429 는 실습 배포의 용량(10 단위)이 작아서 생긴 것으로 보입니다(분당 토큰 한도인지 분당 요청 한도인지는 확인하지 않았습니다). 같은 시간대에 모델을 직접 호출해도 10회 중 4회가 약 5초 걸렸습니다.
  • 시각 읽기: 위 SDK 로그의 시각(16:51)은 이 노트북의 현지 시각(KST)이고, 표 속 서버 스팬의 시각(07:51)은 UTC 입니다. 같은 순간입니다(KST = UTC + 9시간).
  • 시작 전에 거절된 호출은 서버 트레이스에 흔적이 없었습니다. 확인한 것은 ‘없는 모델 배포’로 만든 에이전트를 부른 경우(404)입니다. 요청별 설정을 넣었다가 400 으로 거절된 호출이 트레이스에 남는지는 확인하지 못했습니다.

앱 최소 기록 — 호출 1건당 한 줄에 남길 것

  1. trace_id — 앱이 직접 만들어 traceparent 헤더로 보냅니다. 서버 기록의 operation_Id 와 1:1 로 짝지어집니다.
  2. client_ms — 호출 전 · 후 시간 차(invoke_agents.py 의 출력에서는 ms 라는 이름). 여기서 서버 invoke_agent 시간을 빼면 서버 트레이스가 설명하지 못하는 시간(앱 → 에이전트 구간 · 재시도 대기 등)입니다. 재시도가 있었다면 한 trace_id 에 invoke_agent 스팬이 여러 개이니 모두 합쳐서 빼야 합니다.
  3. status · error — failed · timeout · 429. 거절된 호출은 이 줄이 유일한 기록입니다. 호출이 예외로 끝나는 경우도 한 줄을 남겨야 하므로 try/except 가 필요합니다(아래 스케치).
  4. 재시도 — SDK 로그(OPENAI_LOG=info)로 보거나, 재시도를 끄고(max_retries=0) 시도마다 한 줄씩 기록합니다(가이드 1 의 R3 방식).

예외까지 남기는 앱 최소 기록 — 미검증 스케치입니다. invoke_agents.py 를 바탕으로 한 설명용 코드이며, 구문과 흐름(정상 · failed · 예외)은 가짜 클라이언트로 점검했지만 실제 Foundry 호출로는 실행해 검증하지 않았습니다. 스케치 전체는 호출 코드까지 합쳐 약 20줄이고, 기존 호출 위에 추가되는 줄은 약 10~15줄입니다. 내 앱에 맞게 고쳐 쓰세요.

앱 최소 기록 스케치 — 성공 · 실패 · 예외를 모두 한 줄로 (설명용 · 미검증 · 실행 블록 아님)23줄 · 5개 구간 — 구간마다 아래에 해설이 있습니다 · ‘전체 복사’ 는 구간을 이어 붙인 전체를 복사합니다

import json, secrets, time

def call_agent(client, prompt, conversation=None):
    """에이전트를 한 번 부르고, 성공 · 실패(예외 포함)와 관계없이 JSON 한 줄을 남깁니다."""
    trace_id = secrets.token_hex(16)                 # 서버 기록의 operation_Id 와 1:1 로 짝지을 키
    rec = {"trace_id": trace_id, "status": None, "response_id": None, "error": None}
    options = {"conversation": conversation} if conversation else {}

정리 — 세 가지만 기억하세요

  1. 서버 트레이스는 서버 쪽만 보여 줍니다. 앱 · SDK · 네트워크 · 재시도 대기 · 시작 전에 거절된 호출은 보이지 않습니다.
  2. 그래서 앱은 호출 1건당 한 줄(trace_id · client_ms · status · error)을 남기고, 예외도 try/except 로 잡아 한 줄로 남겨야 합니다.
  3. 이 한 줄의 trace_id 로 서버 기록 전체를 찾고, client_ms 에서 서버 invoke_agent 시간을 뺀 값으로 서버 트레이스에 없는 시간(앱 · SDK · 네트워크 · 재시도 대기 등)을 계산합니다.

직접 해 보기 — 이 장의 표 1 을 내 호출로 만들어 보기

  1. B2 에서 만든 calls.jsonl 에서 한 줄을 골라 ms(클라이언트가 잰 시간)와 trace_id 를 적어 둡니다.
  2. 그 trace_id 로 C4 의 첫 쿼리(trace_by_id)를 실행합니다. 구간 1 의 TID= 줄을 TID=<방금 적어 둔 trace_id> 로 바꾼 뒤 전체를 실행하고, 결과에서 invoke_agent 스팬의 시간을 찾습니다(프롬프트 에이전트는 역할 responsesapi, 호스티드는 역할 agentsv2 요청 행).
  3. ms − invoke_agent 가 그 호출에서 서버 트레이스에 없는 시간(앱 · SDK · 인증 · 네트워크, 그리고 재시도 대기)입니다. 한 trace_id 에 invoke_agent 스팬이 여러 개면(재시도) 모두 합쳐서 빼세요. 호스티드 에이전트의 cold start 호출이라면 서버 invoke_agent 시간에 cold start 가 빠져 있으므로 ms − invoke_agent 에 cold start 시간이 섞여 나옵니다(cold start 시간은 C2 · C3 에서 따로 구합니다).
